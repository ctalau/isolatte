Learn Markdown to DITA

What Microsoft Learn content can do today, which build and test machinery backs it, and how each piece maps to DITA. The port has to keep every one of these strengths. Counts come from the two largest public repositories at pinned commits.

Step 1 · syntactical port

One source file becomes one DITA file

  • Every Learn extension gets its own element or attribute in a learn-dita specialization. Nothing is approximated.
  • Original expressions (moniker ranges, pivot ids, tab ids, snippet ids) are kept verbatim.
  • A reverse converter turns DITA back into Learn Markdown. Parity is a rendered-HTML diff per moniker, pivot and tab.
Step 2 · quality refactorings

Measured, separate, reversible changes

  • Tiny includes become keys; path links become key links.
  • Moniker ranges get a subject-scheme order and are expanded by the build.
  • Pasted duplicates become conrefs; reliable articles become typed topics; cross-file rules move to Schematron with quick fixes.

The hard problems, in order

  1. Contributors write Markdown. Every page has an Edit link into GitHub's web editor, and repositories are open to public pull requests. Copilot instructions and skills in .github/ also target Markdown. Keeping DITA as the only source loses this. The realistic answer for step 1: DITA is the source of truth, and the reverse converter generates Learn Markdown, which keeps feeding the existing OPS build. A Markdown edit from a contributor is converted forward and checked for a clean round trip.
  2. Moniker ranges. 3,338 front-matter expressions in sql-docs use >=, < or ||. DITA filtering has no order. An ordered subject scheme plus a pre-filter step that expands ranges keeps the authoring form and lets DITAVAL do the rest. New releases must not need edits to old topics.
  3. One URL across versions and variants. Learn serves all monikers under one URL (?view=) and all pivots and tabs on one page (?pivots=, ?tabs=). DITA branch filtering produces one output per branch. The HTML step must merge branch outputs back under one URL, or emit Learn Markdown and let OPS do it.
  4. Headings versus blocks. Moniker and zone blocks in Markdown open and close across headings. DITA sections don't nest, and conditional wrappers can't straddle topic boundaries. Step 1 has to split such blocks at each heading and repeat the condition on each piece, then prove the rendered output is unchanged.
  5. Dependent repositories. azure-docs declares 117 dependent repositories (themes, reusable-content, sample code). Includes and :::code point into them through ~/../. The DITA build needs the same pinned checkouts, or keys that resolve into peer maps.
  6. Per-PR latency. OPS builds a preview and posts a build report on every pull request. A DITA-OT run over a 16k-topic map is minutes, not seconds. Incremental builds per changed map are needed before this is acceptable.
Counts are git grep matches in *.md (or the named YAML/JSON files) at the pinned commits. They count syntax, not rendered output; a match inside a code block is included. "Lines" for :::row:::/:::column::: count both opening and closing markers.
