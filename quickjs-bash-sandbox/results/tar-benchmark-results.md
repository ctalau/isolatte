# Tar benchmark results

Generated by `npm run benchmark` (`benchmark/tar-benchmark.mjs`).

- Node.js v22.22.2, 4 vCPUs, run 2026-08-10
- Workload: 1000 files x 2048 bytes each (pseudo-random content, not
  all-zero, cycling through every byte value 0-255), 3 runs per method,
  median reported
- `BashSandbox.tarDirectory()`: a bash script (`tar -cf ...`) executed by
  just-bash's own `tar` command, with the *entire* interpreter -- parsing,
  command dispatch, the tar archive writer (the `modern-tar` library) --
  running as guest code inside a real QuickJS WASM VM (`quickjs-emscripten`).
  Each file read crosses the host/guest boundary through a synchronous
  filesystem bridge scoped to the workspace directory (`src/workspace-fs.mjs`).
  Timing excludes the one-off ~230ms QuickJS runtime + bundle bootstrap
  (`BashSandbox.create()`), matching how you wouldn't count JVM startup in a
  Java benchmark -- a long-lived sandbox amortizes that cost across many
  operations.
- `native tar`: system `tar -cf ... -C <dir> .`, unsandboxed, invoked
  directly via `child_process.execFileSync`

| Method | Median | Runs (ms) | Archive size |
|---|---|---|---|
| `BashSandbox.tarDirectory` (whole interpreter in QuickJS) | 331 ms | 390, 331, 320 | 2501.5 KiB |
| native `tar` | 12 ms | 14, 12, 12 | 2510.0 KiB |

**Slowdown: ~28x vs native `tar`.**

## Why it's slower (and why less slower than the earlier zip approach)

An earlier version of this experiment ran just-bash normally in Node and
only pushed a hand-written zip-archiver into QuickJS via just-bash's
`js-exec` feature -- that measured ~139x slower than native `zip`, because
every file read crossed a synchronous worker-thread/`Atomics.wait` bridge
one file at a time, on top of everything else. This version runs the *whole
interpreter* inside QuickJS instead, using `tar` exactly as just-bash ships
it (no custom archiver, no `js-exec`), and the filesystem bridge is a
direct, same-thread `context.newFunction` call (no worker, no
`Atomics.wait`) -- both interpretation overhead (bytecode vs. native
machine code) and per-file I/O crossing cost remain, but the *architecture*
of the bridge is cheaper. That difference alone took the slowdown from
~139x to ~28x for a structurally similar (many small files, one archive
call) workload.

## Reproduce

```bash
cd quickjs-bash-sandbox
npm install
npm run benchmark
```

Raw captured output from the run behind this table: `tar-benchmark-output.txt`.
Expect a noisy `Aborted(Assertion failed: list_empty(&rt->gc_obj_list) ...)`
line in stderr during each sandboxed run -- that's the known QuickJS
teardown limitation described in `../src/quickjs-runtime.mjs` and
`../README.md`; it's caught, logged, and does not affect the benchmark
numbers or the archive's correctness.
