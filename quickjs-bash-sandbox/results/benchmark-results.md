# Zip benchmark results

Generated by `npm run benchmark` (`benchmark/zip-benchmark.mjs`).

- Node.js v22.22.2, 4 vCPUs, run 2026-08-10
- Workload: 1000 files x 2048 bytes each (pseudo-random content, not
  all-zero), 3 runs per method, median reported
- `BashSandbox.zipDirectory()`: bash script → `js-exec` → archive assembled
  byte-by-byte inside a QuickJS WASM VM (store method, no compression) →
  base64 over stdout → host writes the `.zip`. See
  `../src/zip-bootstrap.mjs` for why it works this way.
- `native zip -0`: system `zip -r -0` (store method — the fair comparison,
  since our sandboxed implementation doesn't compress)
- `native zip` (default): system `zip -r` (deflate) — included for context,
  not a fair method-for-method comparison

| Method | Median | Runs (ms) | Archive size |
|---|---|---|---|
| `BashSandbox.zipDirectory` (QuickJS, store) | 3743 ms | 4045, 3743, 3742 | 2099.6 KiB |
| native `zip -0` (store) | 27 ms | 27.7, 27.0, 26.1 | 2150.4 KiB |
| native `zip` (default, deflate) | 47.7 ms | 47.7, 45.3, 48.0 | 433.6 KiB |

**Slowdown: ~139x vs native `zip -0` (apples-to-apples, store vs store),
~78x vs native `zip`'s default deflate.**

## Why it's slower

Each of the 1000 `fs.readFileSync()` calls made from inside the QuickJS
guest crosses the worker/host bridge synchronously (`Atomics.wait`), on top
of interpreting the bash script itself in JS and running the archive-byte
assembly as interpreted QuickJS bytecode rather than native code. None of
that is a bug — it's the fixed cost of the extra isolation boundary (no
native `zip` binary, no direct filesystem syscalls, every read mediated and
checked) versus a single highly-optimized native process making raw
syscalls. Native `zip` also wins by compressing far less data onto disk
(433.6 KiB vs 2099.6 KiB) despite finishing faster.

## Reproduce

```bash
cd quickjs-bash-sandbox
npm install
npm run benchmark
```

Raw captured output from the run behind this table: `benchmark-output.txt`.
